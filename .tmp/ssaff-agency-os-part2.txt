Core Capabilities
	•	Command routing — receives your Slack commands, determines which orchestrator handles it, dispatches and returns response
	•	Approval queue — consolidates approval requests from all orchestrators into one place. You approve or reject once, CoS routes decision back
	•	Slack Block Kit approvals — every approval request includes asset previews, interactive Approve and Request Changes buttons, and a feedback modal if rejected. Slack templates stored in Supabase (slack_templates table) so they update without touching code
	•	Morning briefing — compiles input from all orchestrators into one structured daily summary at 9am
	•	Escalation management — decides what actually needs to wake you up vs what gets handled automatically
	•	Orchestrator registry — maintains a live registry of every orchestrator, its endpoint, capabilities, and status
	•	Orchestrator spawning — when you need a new capability, CoS scaffolds a new orchestrator repo from template, deploys it to Railway, registers it, and it immediately becomes available
	•	Preference memory — learns your decision patterns over time, reduces approval noise
	•	Doc governance — routes master doc change proposals from doc-agent to approval queue, approves or rejects before any protected section is updated

Orchestrator Registry (Supabase)
	•	orchestrator_registry — every orchestrator: name, repo, Railway endpoint, capabilities, status, last_run
	•	approval_queue — pending decisions from all orchestrators with context and deadline
	•	cos_preferences — your learned decision patterns and routing preferences
	•	slack_templates — Block Kit JSON templates for every message type: approval cards, error alerts, daily digest, job completion, weekly report

Subagent Assignment — How SSAFF Grows
CoS owns the structure of SSAFF. When any new capability is needed — whether you request it or an orchestrator identifies a gap — CoS follows this logic:
	•	Step 1: CoS checks the orchestrator_registry for an existing orchestrator whose domain cleanly covers the new capability
	•	Step 2a: If a clean fit exists — CoS assigns the new subagent under that orchestrator, updates the registry
	•	Step 2b: If no clean fit — CoS defines a new orchestrator with a clear domain, spins it up (new repo, Railway service, registers it), then assigns the subagent under it
	•	No subagent is ever orphaned. Every subagent has an orchestrator. Every orchestrator has a domain.

Example: you say "I need something that monitors Reddit ads"
	•	CoS checks registry — media-buyer-agent owns Facebook Ads, no orchestrator owns Reddit
	•	CoS defines paid-social-agent as new orchestrator (Reddit, TikTok, Pinterest ads)
	•	Spins up CBGROWTHOPS/paid-social-agent, deploys to Railway, registers in orchestrator_registry
	•	Creates reddit-ads-monitor as first subagent under paid-social-agent
	•	Facebook stays under media-buyer-agent — structure stays clean

The orchestrator_registry is the brain of SSAFF. CoS uses it to decide where everything belongs as the system grows.

Slack Commands (examples)
	•	"pause BDN" → routes to media-buyer-agent
	•	"write GTH welcome sequence" → routes to email-agent
	•	"find audiences for pet niche" → routes to growth-agent
	•	"launch new brand [name]" → routes to brand-agent
	•	"status" → pulls ROAS from warehouse, last run from all orchestrators
	•	"approvals" → shows pending approval queue
	•	"create agent for [capability]" → spawns new orchestrator
	•	"update the architecture doc with [change]" → routes to doc-agent → governance-enforcer classifies it → applies or queues for approval

Future interaction model: you interact with SSAFF entirely through CoS in Slack. You ask questions, request updates, approve decisions. You never talk to individual agents directly and you never edit the master doc manually. CoS routes everything to the right agent and surfaces the result back to you.

Working Hours
Agents run on their recommended cron schedules. CoS respects these rules for notifications:

KNOWLEDGE BASE
The Knowledge Base is internal infrastructure — Supabase tables populated exclusively by research-agent, queried by all Layer 1 agents, CoS, and Reach. Not a product. Not sold. The shared intelligence layer that gives every agent institutional memory and gives Reach its data advantage.

Property
Detail
Location
Supabase project rovbqnncmzltdyeeldxz — dedicated tables with pgvector embeddings
Populated by
research-agent exclusively — no other agent writes to Knowledge Base tables
Queried by
All Layer 1 agents, CoS, and Reach product
Access pattern
Semantic search via pgvector cosine similarity — agents ask questions, not SQL queries

OpenAI text-embedding-3-small (1536 dimensions) — generated on every write

How Agents Query It
	•	media-buyer-agent: 'what do we know about baby product buyer seasonality?' → returns relevant research_records ranked by similarity
	•	growth-agent: 'find active communities where remote job seekers discuss side income' → returns ranked community_profiles
	•	creative-agent: 'what content angles are working in the gaming niche this month?' → returns trend_signals + research_records
	•	seo-agent: 'what are competitors targeting for baby product keywords?' → returns competitor_profiles + industry_briefs
	•	Reach: 'find communities for ICP: [description]' → returns ranked community_profiles with engagement scores

How Reach Uses It
Reach does not call research-agent. Reach queries the Knowledge Base directly via Supabase. research-agent populates it. Reach reads it. This separation means Reach can serve external customers using SSAFF's accumulated data without exposing the internal agent infrastructure.

SELF-LEARNING LAYER
SSAFF gets smarter over time through a continuous learning loop. The AI models themselves don't update — but SSAFF's institutional knowledge, system prompts, and decision context improve with every action every agent takes.

Important distinction: the AI doesn't get smarter. SSAFF gets smarter. Claude and Perplexity are pretrained — your data doesn't update their weights. What grows is SSAFF's accumulated context, refined prompts, and pattern recognition built from real operational history.

The Learning Loop
Step
What Happens
1. Agent acts
Every agent action is logged with full context and a quality score
2. Embedding
pgvector embedding generated for every logged record — enables semantic search across all history
3. Weekly analysis
learning-agent reads all scores across all agents, identifies patterns using Claude
4. Prompt update
learning-agent writes refined system prompts back to agent_prompts table with version history
5. Next run
Every agent reads its system prompt from agent_prompts at start of each run — acts with accumulated knowledge
6. Rollback
If a prompt update makes performance worse, learning-agent detects regression and rolls back to previous version automatically

The Knowledge Compounding Effect
Three reasons saving everything matters even though the AI doesn't retrain:

	•	Speed and cost: if research-agent profiled the baby products market last month, it doesn't re-scrape this month — queries the library, fills in only what changed. 10x faster, fraction of the API cost
	•	Cross-agent context: media-buyer-agent asks the knowledge base about seasonal patterns before making budget decisions. creative-agent pulls trend signals into briefs automatically. Agents share institutional memory
	•	Trend detection over time: one scrape tells you what's happening now. A year of saved scrapes tells you what's changing — something Claude can reason over that no single query could reveal

The Opus Exception — learning-agent
learning-agent is the only place in SSAFF where Opus is worth it.

It runs once a week, analyzes patterns across your entire operation, and rewrites system prompts that affect every other agent. A bad prompt update from learning-agent could quietly degrade your whole stack for a week before you notice. That's exactly the high-stakes, low-frequency scenario where Opus pays for itself.

	•	Runs once per week — cost is negligible even at Opus rates (~50k tokens = ~$4/run)
	•	Output quality directly affects every other agent's performance
	•	A reasoning failure here cascades silently across the entire system
	•	The asymmetry is right: small cost increase, catastrophic failure prevention

Model Selection Logic
Rule of thumb for any new agent or subagent added to SSAFF:

	•	Haiku → high volume, short output, templated, structured JSON, speed matters
	•	Sonnet → strategy, synthesis, writing quality, judgment calls, anything customer-facing
	•	Opus → only if Sonnet demonstrably fails at a specific task, or the failure cost is catastrophic

Start with Sonnet everywhere except clear Haiku candidates. Only upgrade to Opus if you see specific reasoning failures. The gap between Sonnet 4 and Opus has narrowed significantly — most tasks Sonnet handles well.

Token Budget Guidelines
Every agent declares a max token budget at the start of each run and tracks usage. Prevents runaway jobs from spiking costs.

	•	Always chunk large documents before sending to Claude — never send raw scraped pages
	•	Summarize with Haiku first, then send summaries to Sonnet for synthesis
	•	research-agent deep-scraper is the highest spike risk — a single deep research job on a new vertical can hit 100k+ tokens without input truncation
	•	Switch from Sonnet to Haiku automatically if a run is trending over budget

BUILDING SSAFF IN CURSOR
Every agent in SSAFF is built in Cursor using Claude models. The model you use for building is as important as the model the agent uses at runtime. Wrong model = sloppy code that looks right but breaks in production.

Model Selection for Building
Task
Model + Why
Architecture decisions
Claude Opus 4 — before writing any code, use Opus to design the system. Ask it to reason through tradeoffs, identify failure modes, and define interfaces between components. Opus thinks deeper. A 10-minute architecture conversation with Opus prevents 10 hours of refactoring.
Writing production code
Claude Sonnet 4 — fast, clean, understands Node.js patterns deeply. Use for all actual implementation once architecture is decided.
Boilerplate and config
Claude Sonnet 4 — package.json, .env.example, Railway config, cron definitions. Fast and accurate.
Debugging and fixing
Claude Sonnet 4 — paste the error, paste the relevant code, it fixes it. Sonnet is faster here than Opus and just as accurate for most bugs.
Complex bugs involving multiple files
Claude Opus 4 — when a bug spans multiple files and the cause isn't obvious, Opus traces the full execution path better.
Code review before deploy
Claude Opus 4 — before deploying any agent to production, have Opus review the full orchestrator loop for logic errors, edge cases, and security issues.

Why This Matters
Sloppy builds create specific failure modes in agentic systems that are hard to debug:

	•	Silent failures — agent runs, logs success, but doesn't actually execute the action. Common when error handling is shallow.
	•	Memory corruption — agent writes malformed data to Supabase, future agent reads it and makes bad decisions based on garbage context.
	•	Infinite loops — orchestrator retries a failed subagent without proper backoff or failure detection.
	•	Token blowout — agent passes entire scraped pages to Claude instead of chunked summaries. $50 job becomes $500.
	•	Race conditions — two subagents write to the same Supabase row simultaneously, one overwrites the other silently.

None of these show up in a quick test. They show up at 2am when the system has been running for three days. Opus architecture review before building and before deploying is the cheapest insurance you have.

Multi-Agent Build Strategy
media-buyer-agent is large enough that building it as one monolithic Cursor session produces worse code than building it in focused sessions per layer. Each session has one job.

Session
Build Target + Model
Session 0 — Architecture
Opus 4: paste the media-buyer-agent playbook section, ask Opus to define all interfaces, data shapes, and error handling patterns before any code is written. Output: interface definitions document.
Session 1 — Integrations
Sonnet 4: build integrations/ folder. facebook.js, maxbounty.js, bemob.js, supabase.js, slack.js, monday.js, creative-agent.js. Each one tested independently before moving on.
Session 2 — Memory Layer
Sonnet 4: build memory/ folder. decisions.js, retrieval.js, pgvector queries. Feed it the Supabase schema from the migrations file.
Session 3 — Subagents
Sonnet 4: build subagents/ folder one file at a time. campaign-manager, budget-optimizer, audience-builder, attribution-auditor, offer-monitor, social-poster. Each subagent only uses integrations built in Session 1.
Session 4 — Orchestrator
Opus 4: the orchestrator/index.js is the most complex file — it coordinates all subagents, calls Claude for decisions, manages the decision loop. Use Opus to write this. The orchestrator is where silent failures hide.
Session 5 — Server + Cron
Sonnet 4: server.js Express endpoints, Slack Bolt commands, cron/schedule.js. Straightforward once the orchestrator works.
Session 6 — Review + Deploy
Opus 4: full codebase review before touching Railway. Ask Opus to find every place where an error could be swallowed silently, every place where a retry could become infinite, every place where token usage could spike. Fix everything it finds before deploying.

Context Management Between Sessions
Each Cursor session starts fresh. How you hand off context between sessions determines whether the code is coherent or fragmented.

	•	End every session by asking Cursor to write a HANDOFF.md — what was built, what interfaces were defined, what assumptions were made, what's left
	•	Start every session by feeding it: the HANDOFF.md from the previous session + the specific files it needs to reference + the playbook section for what it's building
	•	Never start a new session without context — Cursor will make up interfaces that conflict with what was built
	•	Keep a running DECISIONS.md that logs every architectural choice and why — when you revisit code three weeks later you need to know why something was built the way it was

Testing Before Deploying
Every agent has three test levels before it touches production:

	•	Unit test: run each subagent in isolation with mock data. Confirm it produces the right output format before wiring it to live APIs
	•	Integration test: run the full orchestrator loop with real API connections but read-only mode. No writes to Facebook, no Slack messages sent. Confirm data flows correctly.
	•	Canary deploy: deploy to Railway but only trigger manually via POST /run. Run it manually three times on consecutive days. Review every log entry. Only enable cron after three clean manual runs.


CROSS-AGENT STANDARDS
Patterns every agent in SSAFF follows. Added to the orchestrator-template so all current and future agents inherit them.

pgvector Memory — Semantic Search
All agent memory tables use pgvector embeddings for semantic search. Instead of exact keyword matching, agents find past decisions based on meaning — "find times we dealt with a situation like this."

	•	Enable pgvector extension in Supabase: CREATE EXTENSION vector
	•	Add embedding column (vector 1536) to agent_decisions, feedback, client_research tables
	•	On every write: generate embedding via OpenAI text-embedding-3-small, store alongside the record
	•	On every retrieval: query by cosine similarity instead of keyword — returns semantically relevant past decisions
	•	Result: agents learn from nuanced situational context, not just matching exact field values

Error Handling — Exponential Backoff
Every external API call in every agent follows this pattern:

	•	Retry up to 3 times with exponential backoff: 2s, 8s, 32s
	•	After 3 failures: log to Supabase error_logs table with job_id, agent, failed_step, error_message
	•	Post error card to #alerts-critical via CoS escalation
	•	Job status set to failed — does not block other running jobs
	•	Error card includes Retry button that re-queues the job

Job State Machine — creative-agent and video-agent
Every content and video production job moves through a defined state stored in Supabase. Agents check and update state at every step.

access-manager — CoS Subagent
access-manager solves the permissions and credential routing problem. Every orchestrator needs different secrets. Without access-manager you'd manually configure Keygent and Railway for every new agent. With access-manager, CoS calls it once and the new orchestrator is fully provisioned with exactly the right access and nothing more.

The Problem It Solves
	•	13 orchestrators each need different subsets of secrets
	•	Manually provisioning each one in Keygent and Railway is error-prone and slow
	•	An orchestrator with too many secrets is a security risk — media-buyer-agent doesn't need MailerLite keys
	•	An orchestrator with missing secrets fails silently at runtime
	•	access-manager solves all three: automatic, correct, minimal permissions

How It Works
Step
What Happens
1. Trigger
CoS registers new orchestrator in orchestrator_registry — calls access-manager with orchestrator name
2. Look up permissions
access-manager queries orchestrator_permissions table — gets exact list of secrets this orchestrator is allowed
3. Create portal token
Calls Keygent API — creates new portal token scoped to only those secrets
4. Set Railway env var
Calls Railway API — sets KEYGENT_PORTAL_TOKEN on the new service
5. Audit log
Writes to access_grants table — what was provisioned, when, for which orchestrator
6. Confirm
Posts to #agency-command — access provisioned for [orchestrator] with list of granted secrets

Doc System Architecture
Three layers. Agents update layers 2 and 3. Layer 1 requires your approval.

Layer
Contents + Rules
Layer 1 — Master Doc
SSAFF.md — the constitution. Architecture, roles, rules, boundaries, naming, ownership, approval logic, system standards. Agent readable. Human approved changes only. doc-agent proposes, CoS routes to you.
Layer 2 — Derived Docs
Agent spec docs, repo READMEs, API contracts, runbooks, integration docs, deployment docs, QA docs, schema references. Machine writable. doc-agent generates and maintains these automatically.
Layer 3 — Change Logs
Proposed changes, diff summaries, version notes, migration notes, open questions, dependency impacts. Fully autonomous. doc-agent writes all of this without approval.

Protected Sections — Approval Required
doc-agent never edits these without CoS routing to your approval queue first:

	•	Spend approval thresholds
	•	System architecture and layer definitions
	•	Security rules and access controls
	•	Agent boundaries and orchestrator ownership

	•	Test plans and QA docs
	•	Prompt versions in agent_prompts table

Metadata Fields — Every Master Doc Section
Adding these fields to every major section makes the master doc machine-readable and agent-friendly:

	•	Owner — who is responsible for this section
	•	Source of truth — yes/no
	•	Agent writable — yes/no
	•	Approval required — yes/no
	•	Derived docs — which docs/10_agents/ or docs/20_systems/ files are generated from this section
	•	Related repos — which GitHub repos this section covers
	•	Related agents — which orchestrators this section defines or affects
	•	Last approved date — when a human last reviewed and approved this section

Subagents

Core Writing
	•	master-doc-reader — reads SSAFF master doc, extracts structured data per section. Read only. Called first by every other subagent. The source of truth parser.
	•	spec-writer — generates derived spec docs for each orchestrator from master doc. When capabilities change in master, regenerates the corresponding docs/10_agents/*.md file automatically.
	•	readme-writer — keeps every repo README in sync with master doc. Pushes updates via GitHub API when an orchestrator's spec changes.
	•	runbook-writer — generates operational runbooks from escalation rules, QA processes, and deployment steps. Produces docs/30_operations/ files.
	•	api-contract-writer — calls every orchestrator's GET /capabilities and GET /subagents endpoints, generates API contract docs in docs/40_generated/api-contracts/
	•	schema-sync — reads Supabase schema, compares against master doc schema section. Flags mismatches. Updates schema reference docs after migrations run.
	•	env-sync — reads every .env.example across all repos, generates consolidated env var reference. Flags vars that exist in code but aren't documented in master.

Governance
	•	change-classifier — reads every proposed doc change, classifies it: safe to auto-apply / needs approval / touches protected section. Routes accordingly. The gatekeeper.
	•	conflict-detector — before any doc update is applied, checks whether it contradicts master doc, another derived doc, or the codebase. Blocks conflicting changes and explains why.
	•	governance-enforcer — watches for changes to protected sections. Routes all protected changes to CoS approval queue before anything gets written. Never bypassed.

Changelog and Audit
	•	changelog-writer — after every approved change, writes human-readable changelog entry: what changed, why, which master doc section it derived from, who approved it.
	•	version-tracker — maintains version numbers on every doc. Every write increments version. Keeps full history for rollback to any previous state.
	•	audit-reporter — weekly report to #agency-command: what docs were updated, what was proposed but rejected, what's out of sync, what needs attention.

Automation
	•	sync-scheduler — runs doc sync jobs on schedule: schema-sync daily after migrations, readme-writer on every GitHub push, spec-writer weekly or on master doc change.
	•	drift-detector — compares codebase reality against documentation daily. Flags new files, env vars, or subagents that exist in code but aren't documented. Prevents silent documentation rot.
